## 集合

### 问题 001：Java 集合框架中 List、Set 和 Map 的区别

#### 时间
2026-03-26

#### 问题
说一下 Java 集合框架中 List、Set 和 Map 的区别。

#### 回答
一句话回答：

List 负责存有序可重复的数据。

Set 负责存无序或弱有序但不可重复的数据。

Map 负责存键值对，key 不可重复，value 可以重复。

面试回答：

- List、Set 都继承自 `Collection`。
- Map 不属于 `Collection` 体系。
- Map 是单独的一套键值对结构。

- List 的特点是有序、可重复、可通过下标访问。
- 适合存一组有顺序要求的数据。
- 常见实现类有 `ArrayList`、`LinkedList`。

- Set 的特点是元素不可重复。
- 一般不提供按下标访问。
- 适合做去重。
- 常见实现类有 `HashSet`、`LinkedHashSet`、`TreeSet`。

- Map 的特点是按 `key-value` 存储。
- `key` 不能重复。
- `value` 可以重复。
- 适合根据 key 快速查找 value。
- 常见实现类有 `HashMap`、`LinkedHashMap`、`TreeMap`、`ConcurrentHashMap`。

- List 里判断重复不是强约束，可以放重复元素。
- Set 底层通常依赖 `hashCode()` 和 `equals()` 判断是否重复。
- Map 里也是通过 key 的 `hashCode()` 和 `equals()` 判断 key 是否重复。

- 如果面试官继续追问实现原理：
- `ArrayList` 底层是数组。
- `LinkedList` 底层是双向链表。
- `HashSet` 底层通常基于 `HashMap`。
- `HashMap` 底层是数组 + 链表 + 红黑树。

高频追问：

- `ArrayList` 和 `LinkedList` 区别
- `HashSet` 为什么不能重复
- `HashMap` 底层结构
- `List` 和数组区别
- `HashMap` 和 `ConcurrentHashMap` 区别

扣分点：

- 只会说 List 有序、Set 无序、Map 键值对，太浅
- 不知道 Map 不属于 `Collection`
- 不知道 Set 去重和 Map key 去重都依赖 `hashCode()` 和 `equals()`
- 不知道常见实现类和适用场景

#### 关键词
Java集合, List, Set, Map, ArrayList, HashSet, HashMap

##### 追问 1
问题：ArrayList 和 LinkedList 区别

回答：
核心结论：

`ArrayList` 底层是动态数组。

`LinkedList` 底层是双向链表。

查找上 `ArrayList` 更适合，插入删除上 `LinkedList` 理论更有优势，但实际开发里 `ArrayList` 更常用。

1. 底层结构不同

- `ArrayList` 底层是数组。
- `LinkedList` 底层是双向链表。

2. 随机访问性能不同

- `ArrayList` 支持按下标快速访问。
- 因为数组内存连续，访问效率高。
- `LinkedList` 按下标访问需要从头或尾遍历。
- 所以随机访问慢。

3. 插入删除性能不同

- `ArrayList` 在尾部插入通常较快。
- 但中间插入、删除时，可能需要移动大量元素。
- `LinkedList` 在已知节点位置时，插入删除只需要改指针。
- 但如果先要查位置，还是要遍历，所以未必就快。

4. 内存占用不同

- `ArrayList` 主要是数组本身占空间。
- `LinkedList` 每个节点还要额外保存前驱和后继指针。
- 所以 `LinkedList` 通常更占内存。

5. 使用场景不同

- 查询多、尾插多，优先 `ArrayList`。
- 频繁头尾插入删除，可以考虑 `LinkedList`。
- 但业务开发里，大多数场景直接用 `ArrayList`。

面试怎么答：

- `ArrayList` 底层是动态数组，`LinkedList` 底层是双向链表。
- `ArrayList` 随机访问快，`LinkedList` 随机访问慢。
- `LinkedList` 理论上插入删除更方便，但前提是已经定位到节点。
- 如果算上查找过程，很多场景下 `ArrayList` 反而更实用。

扣分点：

- 只会背数组和链表，不会结合访问、插入、内存一起答
- 说 `LinkedList` 插入删除一定比 `ArrayList` 快，太绝对

##### 追问 2
问题：HashSet 为什么不能重复

回答：
核心结论：

`HashSet` 不能重复，本质是因为它底层基于 `HashMap`，插入元素时会先比较 `hashCode()`，再比较 `equals()`。

如果判定是同一个元素，就不会再放进去。

1. 底层结构

- `HashSet` 底层其实就是 `HashMap`。
- 只不过 `HashSet` 只用 `HashMap` 的 key 存数据。
- value 用的是一个固定占位对象。

2. 添加元素时的流程

- 先调用元素的 `hashCode()` 算 hash。
- 再根据 hash 定位数组下标。
- 如果该位置没有元素，直接插入。
- 如果该位置有元素，就继续比较。

3. 怎么判断重复

- 先比 `hashCode()`。
- 如果 hash 不同，通常不是同一个元素。
- 如果 hash 相同，再调用 `equals()` 比较。
- 只有 `hashCode()` 相同并且 `equals()` 也为 `true`，才认为是重复元素。

4. 为什么要同时比较

- 因为不同对象可能 hash 冲突。
- 不能只靠 `hashCode()` 判断。
- 最终是否重复，还要看 `equals()`。

面试怎么答：

- `HashSet` 底层基于 `HashMap`。
- 添加元素时会先算 `hashCode()` 定位桶位置。
- 如果发生冲突，再用 `equals()` 比较。
- 如果两者判断是同一个对象，就不会重复插入。

扣分点：

- 只说 `HashSet` 不能重复，但说不出底层依赖 `HashMap`
- 只提 `hashCode()`，不提 `equals()`
- 说 hash 相同就一定重复，这是错的

##### 追问 3
问题：HashMap 底层原理

回答：
核心结论：

`HashMap` 底层是数组 + 链表 + 红黑树。

它通过 key 的 `hashCode()` 计算存储位置，用空间换时间，提高查找效率。

1. 基本结构

- JDK 1.8 之后，`HashMap` 底层主要是数组。
- 数组每个位置叫一个桶。
- 桶里可能挂链表或红黑树。

2. put 流程

- 先对 key 计算 `hashCode()`。
- 再做扰动运算，减少 hash 冲突。
- 根据结果和数组长度计算桶下标。
- 如果桶为空，直接插入。
- 如果桶不为空，说明发生 hash 冲突。

3. 冲突怎么处理

- 如果桶里是链表，就逐个比较 key。
- 比较时会用 `hash` 和 `equals()`。
- 如果 key 相同，就覆盖旧 value。
- 如果 key 不同，就挂到链表后面。

- 在 JDK 1.8 中，如果链表长度超过阈值，且数组容量达到要求，会把链表转成红黑树。
- 这样是为了降低极端情况下链表过长导致的查询性能问题。

4. 为什么需要扩容

- `HashMap` 默认容量是 16。
- 默认负载因子是 0.75。
- 当元素个数超过 `容量 * 负载因子` 时，会触发扩容。
- 扩容后会重新计算元素位置，也就是 rehash。

5. get 流程

- 先算 key 的 hash。
- 定位到对应桶。
- 如果桶里只有一个节点，直接返回。
- 如果是链表，就遍历查找。
- 如果是红黑树，就按树方式查找。

6. 为什么线程不安全

- `HashMap` 没有加锁。
- 多线程同时 put/get 可能出现数据覆盖、数据不一致等问题。
- 并发场景一般用 `ConcurrentHashMap`。

面试怎么答：

- `HashMap` 底层是数组 + 链表 + 红黑树。
- put 时先通过 key 的 `hashCode()` 定位桶下标。
- 如果冲突，就在桶里用链表或红黑树继续查找。
- key 相同就覆盖，不同就新增。
- 元素过多会扩容，链表过长在 JDK 1.8 会树化。

高频考点：

- 为什么要扰动函数
- 为什么负载因子默认是 0.75
- 为什么 JDK 1.8 引入红黑树
- `HashMap` 为什么线程不安全

扣分点：

- 还在答 JDK 1.7 的纯数组加链表，不知道 1.8 加了红黑树
- 只会说数组加链表，不会说 put/get 流程
- 不知道 key 是否重复靠 `hash` + `equals()`

##### 追问 4
问题：HashMap 为什么线程不安全

回答：
核心结论：

`HashMap` 线程不安全，本质是因为它在并发读写时没有加锁，也没有其他并发控制机制。

多个线程同时操作时，可能出现数据覆盖、数据丢失、读到脏数据、扩容异常等问题。

1. put 不是原子操作

- `HashMap` 的 put 包含算 hash、定位桶、插入节点、可能扩容等多个步骤。
- 这些步骤不是原子完成的。
- 多线程同时 put，可能互相覆盖结果。

2. 并发修改会导致数据不一致

- 两个线程同时往同一个桶插入元素。
- 可能一个线程刚插进去，另一个线程又覆盖链表结构。
- 最终可能造成数据丢失。

3. 扩容时问题更明显

- `HashMap` 扩容时会 rehash。
- 多线程同时扩容或迁移数据时，链表/桶结构可能被破坏。
- 在老版本 JDK 里，极端情况下还可能形成死循环。

4. 读也不一定安全

- 很多人以为只有写不安全。
- 其实如果一个线程在写，另一个线程在读，也可能读到中间状态的数据。
- 因为没有可见性和一致性保障。

面试怎么答：

- `HashMap` 线程不安全，因为它没有加锁。
- put、resize 都是多步骤操作，不具备原子性。
- 多线程并发下可能出现数据覆盖、数据丢失、结构异常。
- 所以并发场景一般用 `ConcurrentHashMap`。

扣分点：

- 只会说“因为没加锁”
- 说不出具体会有什么问题
- 不知道扩容阶段是高风险点

##### 追问 5
问题：ConcurrentHashMap 底层原理

回答：
核心结论：

`ConcurrentHashMap` 是线程安全的哈希表。

JDK 1.8 里它的核心思路是“数组 + 链表 + 红黑树 + CAS + synchronized”，通过更细粒度的并发控制提高性能。

1. 基本结构

- JDK 1.8 的 `ConcurrentHashMap` 底层结构和 `HashMap` 很像。
- 也是数组 + 链表 + 红黑树。
- 但它在并发控制上做了专门设计。

2. put 时怎么保证线程安全

- 如果桶位置为空，优先用 CAS 尝试插入。
- CAS 成功就直接放进去，不需要加锁。
- 如果桶不为空，说明发生冲突。
- 这时会对当前桶加锁，而不是锁整个表。

3. 锁粒度更细

- 它不是像 `Hashtable` 一样给整个 Map 加大锁。
- 而是只锁当前冲突的桶或链表头节点。
- 所以并发性能更高。

4. 链表过长也会树化

- 和 `HashMap` 类似。
- 当桶里链表过长时，也会转成红黑树。
- 目的是减少极端冲突下的查询时间。

5. get 为什么效率高

- `get` 大多数场景不加锁。
- 因为节点的关键字段用了 `volatile`，保证可见性。
- 所以读性能通常比较好。

6. 扩容怎么做

- `ConcurrentHashMap` 也会扩容。
- 但扩容时支持多线程协助迁移数据。
- 不是简单粗暴地整表锁死。

7. JDK 1.7 和 1.8 的区别

- JDK 1.7 用的是 `Segment` 分段锁。
- JDK 1.8 去掉了 `Segment`。
- 改成 `CAS + synchronized`，锁粒度更细，实现也更简洁。

面试怎么答：

- `ConcurrentHashMap` 底层也是数组 + 链表 + 红黑树。
- JDK 1.8 通过 CAS 和 `synchronized` 保证并发安全。
- 空桶插入用 CAS，冲突时只锁当前桶，不锁整个表。
- `get` 大多数时候不加锁，所以性能比 `Hashtable` 更好。

高频考点：

- JDK 1.7 和 1.8 的 `ConcurrentHashMap` 区别
- 为什么 `ConcurrentHashMap` 读性能高
- 为什么它比 `Hashtable` 性能好
- CAS 和 `synchronized` 分别用在什么场景

扣分点：

- 还在只背分段锁，不知道 1.8 已经改了
- 说不出 `ConcurrentHashMap` 和 `HashMap` 结构上的相似点
- 不知道它是细粒度锁，不是整表锁

##### 追问 6
问题：为什么负载因子默认 0.75

回答：
核心结论：

负载因子决定 `HashMap` 什么时候扩容。

默认取 `0.75`，本质是时间和空间的折中。

它既不会太浪费空间，也能把 hash 冲突控制在比较合理的范围内。

1. 负载因子是什么

- 负载因子就是扩容阈值比例。
- 公式可以记成：`阈值 = 容量 * 负载因子`。
- 比如容量 16，负载因子 0.75。
- 那元素达到 12 时就会触发扩容。

2. 为什么不能太小

- 如果负载因子很小，比如 0.5。
- 扩容会更早发生。
- 冲突确实会少一些。
- 但空间利用率低，扩容次数也可能变多。

3. 为什么不能太大

- 如果负载因子很大，比如 1 或更高。
- 数组能装得更满。
- 但桶冲突概率会明显上升。
- 链表或树更容易变长。
- 查询性能会下降。

4. 为什么 0.75 比较合适

- 0.75 是经验上比较平衡的值。
- 空间利用率还可以。
- 冲突率也能控制住。
- 扩容频率和查询效率之间取得了较好的折中。

面试怎么答：

- 负载因子决定 `HashMap` 的扩容时机。
- 太小会频繁扩容，浪费空间。
- 太大会增加 hash 冲突，影响查询效率。
- 默认 0.75 是时间和空间的折中值。

扣分点：

- 只会背默认是 0.75，不知道原因
- 不知道负载因子本质控制的是扩容阈值
- 不知道它是在“扩容频率”和“冲突概率”之间做平衡

##### 追问 7
问题：HashMap 和 ConcurrentHashMap 区别

回答：
核心结论：

`HashMap` 是非线程安全的。

`ConcurrentHashMap` 是线程安全的。

两者底层结构相似，但并发控制机制完全不同。

1. 线程安全性不同

- `HashMap` 不保证线程安全。
- 多线程并发读写可能出现数据覆盖、丢失、结构异常。

- `ConcurrentHashMap` 保证并发场景下的线程安全。
- 适合多线程读写。

2. 并发控制不同

- `HashMap` 没有加锁，也没有 CAS 控制。
- `ConcurrentHashMap` 在 JDK 1.8 里主要用 `CAS + synchronized`。
- 空桶插入优先 CAS。
- 冲突时只锁当前桶。

3. 性能表现不同

- 单线程场景下，`HashMap` 更轻量。
- 并发场景下，`ConcurrentHashMap` 更安全，也更适合高并发。
- 它比 `Hashtable` 性能好，因为不是整表锁。

4. null 支持不同

- `HashMap` 允许一个 `null key`，也允许多个 `null value`。
- `ConcurrentHashMap` 不允许 `null key`，也不允许 `null value`。

5. 使用场景不同

- 单线程或明确无并发问题，用 `HashMap`。
- 多线程共享 Map，用 `ConcurrentHashMap`。

面试怎么答：

- `HashMap` 和 `ConcurrentHashMap` 最大区别是线程安全。
- `HashMap` 线程不安全，`ConcurrentHashMap` 线程安全。
- JDK 1.8 的 `ConcurrentHashMap` 底层通过 `CAS + synchronized` 做细粒度并发控制。
- 另外 `HashMap` 允许 `null`，`ConcurrentHashMap` 不允许。

扣分点：

- 只会说一个安全一个不安全
- 不知道 `ConcurrentHashMap` 的核心并发机制
- 不知道两者对 `null` 的支持不同

##### 追问 8
问题：CAS 是什么

回答：
核心结论：

CAS 是 Compare And Swap，比较并交换。

它是一种无锁并发机制。

核心思想是：先比较内存中的值是不是预期值，如果是，就更新；如果不是，就说明有线程改过了，本次更新失败。

1. CAS 解决什么问题

- 多线程同时修改一个共享变量时，如果直接改，可能出线程安全问题。
- CAS 想解决的是：不加传统大锁，也能安全更新数据。

2. CAS 三个核心值

- 旧值，通常叫预期值。
- 新值，准备改成什么。
- 当前内存值。

3. 执行流程

- 先拿到一个旧值。
- 准备把它改成新值。
- 更新前先比较当前内存值是否还等于旧值。
- 如果相等，说明期间没人改过，可以更新成功。
- 如果不相等，说明别的线程已经改过了，本次更新失败，一般会重试。

4. 优点

- 不一定需要阻塞线程。
- 在竞争不激烈时性能很好。
- 是很多并发类的基础。

5. 缺点

- 高并发冲突严重时，自旋重试会浪费 CPU。
- 还有 ABA 问题。
- 只能保证单个共享变量的原子更新，复杂场景处理有限。

6. 常见应用

- `AtomicInteger`
- `ConcurrentHashMap`
- `AQS` 的部分实现

面试怎么答：

- CAS 就是比较并交换。
- 更新变量前，先比较当前值和预期值是否一致。
- 一致才更新，不一致就失败或重试。
- 它是一种无锁并发思想，常用于原子类和并发容器。

高频考点：

- CAS 为什么是无锁
- CAS 有什么问题
- ABA 问题是什么
- 自旋开销是什么

扣分点：

- 只会背英文全称
- 不知道它怎么保证线程安全
- 不知道 CAS 失败后通常要重试

##### 追问 9
问题：为什么 ConcurrentHashMap 的 get 不加锁也能安全

回答：
核心结论：

`ConcurrentHashMap` 的 `get` 大多数情况下不加锁还能安全，核心原因是它的关键节点字段具备可见性保障，而且读操作本身不修改结构。

简单说，就是写的时候已经把该保证的可见性和发布时机处理好了，所以读线程可以安全看到最新或合法状态的数据。

1. get 为什么通常不加锁

- `get` 本质是读操作。
- 它不需要修改桶结构。
- 所以没必要像写操作一样加锁。

2. 为什么不加锁还能看到正确数据

- `ConcurrentHashMap` 里很多关键字段用了 `volatile`。
- 比如数组引用、节点 value、next 等关键位置。
- `volatile` 能保证可见性。
- 一个线程写入后，其他线程能及时看到。

3. 写操作已经做了同步控制

- 写的时候不是随便写。
- 空桶插入用 CAS。
- 冲突时对桶加锁。
- 所以写入过程会保证结构处于可用状态。

4. 读到的为什么至少是合法状态

- 因为节点发布出去之前，该初始化的信息已经写好。
- 发布后，读线程看到的要么是旧值，要么是新值。
- 不会看到完全乱掉的中间结构。

5. 为什么它读性能高

- 因为 `get` 不需要整表加锁。
- 多线程可以并发读。
- 这也是它性能优于 `Hashtable` 的重要原因之一。

面试怎么答：

- `ConcurrentHashMap` 的 `get` 大多数情况下不加锁。
- 因为读操作不修改数据结构。
- 它依赖 `volatile` 保证可见性，依赖 CAS 和桶级锁保证写入有序和安全发布。
- 所以读线程虽然不加锁，也能读到合法数据。

扣分点：

- 只会说“因为用了 volatile”
- 不知道写操作的同步控制同样重要
- 说成“绝对实时读到最新值”，表述太死
- 更准确的说法是：能看到线程安全下的合法可见结果

##### 追问 10
问题：ABA 问题是什么

回答：
核心结论：

ABA 问题是 CAS 的经典问题。

一个变量的值从 A 变成 B，又变回 A。

这时另一个线程用 CAS 去比较，发现还是 A，就会误以为这个值从来没变过。

1. 为什么会有 ABA

- CAS 只比较“当前值”和“预期值”是否相等。
- 它不关心这个值中间有没有被别人改过。
- 只要最后看起来还是 A，CAS 就可能认为没问题。

2. 举个例子

- 线程 1 读取到变量值是 A，准备把它改成 C。
- 在线程 1 真正更新前，线程 2 先把 A 改成 B。
- 然后线程 2 又把 B 改回 A。
- 线程 1 再执行 CAS 时，发现当前值还是 A，就更新成功。
- 但实际上这个值已经被别的线程改过两次了。

3. 问题本质

- CAS 只能判断“值有没有变”。
- 但有些场景真正关心的是“这个值有没有被动过”。
- 这就是 ABA 问题。

4. 怎么解决

- 常见做法是加版本号。
- 不只比较值，还比较版本。
- Java 里常见类是 `AtomicStampedReference`。
- 每次修改时，值和版本号一起更新。

面试怎么答：

- ABA 是 CAS 的一个问题。
- 一个值从 A 变成 B 再变回 A，CAS 只看最终值，可能误以为没变过。
- 所以有些场景要加版本号，比如用 `AtomicStampedReference` 解决。

扣分点：

- 只会背“A 变 B 再变 A”
- 说不出它为什么会影响 CAS
- 不知道版本号方案

##### 追问 11
问题：AtomicInteger 底层原理

回答：
核心结论：

`AtomicInteger` 底层核心就是 `volatile + CAS`。

它通过 CAS 保证自增、自减这类操作的原子性，而不是用 `synchronized` 加锁。

1. 为什么普通 i++ 不安全

- 因为 `i++` 不是原子操作。
- 它至少分读取、加一、写回三步。
- 多线程同时执行时会丢失更新。

2. AtomicInteger 怎么做

- `AtomicInteger` 内部有一个 `volatile int value`。
- `volatile` 保证可见性。
- 真正更新时，通过 CAS 比较并交换。

3. 以 `incrementAndGet()` 为例

- 先取当前值。
- 计算新值 `old + 1`。
- 再用 CAS 尝试把旧值改成新值。
- 如果比较失败，说明别的线程改过了。
- 就重新取值，再继续 CAS，直到成功。

4. 为什么它比锁轻

- 它不一定阻塞线程。
- 竞争不激烈时效率通常比重量级锁更好。
- 但如果竞争很激烈，自旋重试也会消耗 CPU。

5. 底层依赖什么

- JDK 早期可以记 `Unsafe`。
- 新版也可以理解成依赖底层原子指令支持。
- 面试重点不是背源码类名，而是说清楚 `volatile + CAS + 自旋`。

面试怎么答：

- `AtomicInteger` 底层是 `volatile + CAS`。
- `value` 用 `volatile` 保证可见性。
- 自增时会先取旧值，再 CAS 更新。
- 如果失败就自旋重试，直到成功。

高频考点：

- `AtomicInteger` 为什么线程安全
- 为什么 `i++` 不是原子操作
- `AtomicInteger` 和 `synchronized` 区别
- 自旋的代价是什么

扣分点：

- 只会说它是原子类
- 不知道底层依赖 CAS
- 不知道失败后会自旋重试

##### 追问 12
问题：synchronized 和 ReentrantLock 区别

回答：
核心结论：

`synchronized` 是 Java 内置关键字。

`ReentrantLock` 是 JDK 提供的显示锁。

两者都能实现线程同步，但使用方式和功能侧重点不同。

1. 用法不同

- `synchronized` 用关键字修饰方法或代码块。
- 用法简单，出了作用域会自动释放锁。

- `ReentrantLock` 需要手动 `lock()` 和 `unlock()`。
- 一般要配合 `try-finally`，否则可能忘记释放锁。

2. 功能不同

- `synchronized` 功能相对基础。
- `ReentrantLock` 功能更丰富。
- 它支持可中断锁、可轮询尝试加锁、可设置公平锁。
- 还支持多个 `Condition` 做更细粒度线程协作。

3. 锁释放方式不同

- `synchronized` 执行完代码块或方法后，JVM 自动释放锁。
- `ReentrantLock` 必须显式释放。

4. 性能理解

- 早期大家常说 `ReentrantLock` 性能更好。
- 但现在 `synchronized` 已经优化很多了，比如偏向锁、轻量级锁等。
- 面试里不要绝对化说谁一定更快。
- 更准确的说法是：简单同步场景用 `synchronized` 很常见，复杂控制场景 `ReentrantLock` 更灵活。

5. 适用场景

- 代码简单、同步逻辑直接，优先 `synchronized`。
- 需要中断、超时、多个条件队列、公平锁时，用 `ReentrantLock`。

面试怎么答：

- `synchronized` 是关键字，`ReentrantLock` 是显示锁。
- `synchronized` 自动释放锁，使用简单。
- `ReentrantLock` 要手动加锁解锁，但功能更丰富。
- 比如支持可中断、超时尝试、公平锁和多个 `Condition`。

高频考点：

- 什么是可重入
- 什么是公平锁和非公平锁
- 为什么 `unlock()` 要放 `finally`
- `Condition` 和 `wait/notify` 区别

扣分点：

- 只会说一个是关键字一个是类
- 不知道 `ReentrantLock` 的增强能力
- 不知道 `synchronized` 自动释放，`ReentrantLock` 要手动释放

##### 追问 13
问题：volatile 和 synchronized 区别

回答：
核心结论：

`volatile` 解决的是可见性和有序性问题。

`synchronized` 解决的是可见性、有序性和原子性问题。

所以两者不是一个层级的东西，`synchronized` 能力更强。

1. 保证内容不同

- `volatile` 保证一个线程修改变量后，其他线程能马上看到。
- 它还能禁止部分指令重排序。
- 但它不能保证复合操作的原子性。

- `synchronized` 不但保证可见性和有序性。
- 还保证同一时刻只有一个线程进入临界区。
- 所以它能保证原子性。

2. 使用场景不同

- `volatile` 适合一个线程写、多个线程读，或者状态标记这类场景。
- 比如停止标志位。

- `synchronized` 适合多个线程同时修改共享变量。
- 或者一段业务逻辑必须整体加锁执行。

3. 性能和开销理解

- `volatile` 更轻量，因为它不会阻塞线程。
- `synchronized` 涉及加锁和竞争，开销通常更大。
- 但面试里不要绝对说谁一定更快，要结合场景。

4. 典型例子

- `volatile int count` 不能保证 `count++` 线程安全。
- 因为 `count++` 是读、改、写三步。
- 这时要用 `synchronized` 或 CAS。

面试怎么答：

- `volatile` 主要保证可见性和禁止重排序，不保证原子性。
- `synchronized` 通过加锁保证可见性、原子性和有序性。
- 所以简单状态标记可以用 `volatile`，临界区共享数据修改一般用 `synchronized`。

扣分点：

- 说 `volatile` 能保证线程安全，这不严谨
- 不知道 `volatile` 不能保证 `i++`
- 不知道两者都能保证可见性

##### 追问 14
问题：线程池核心参数

回答：
核心结论：

线程池最核心的参数是这 7 个：

- `corePoolSize`
- `maximumPoolSize`
- `keepAliveTime`
- `unit`
- `workQueue`
- `threadFactory`
- `handler`

面试里要重点讲前 5 个，加上拒绝策略。

1. corePoolSize

- 核心线程数。
- 即使线程空闲，默认也会保留的线程数量。

2. maximumPoolSize

- 最大线程数。
- 当核心线程满了，队列也满了，线程池才会继续创建线程，直到这个上限。

3. keepAliveTime

- 非核心线程空闲多久会被回收。
- 通常和 `maximumPoolSize` 配合看。

4. workQueue

- 任务阻塞队列。
- 新任务进来时，如果核心线程都忙，任务会先进入队列等待。
- 常见有 `LinkedBlockingQueue`、`ArrayBlockingQueue`、`SynchronousQueue`。

5. threadFactory

- 线程工厂。
- 用来创建线程。
- 一般可以自定义线程名，方便排查问题。

6. handler

- 拒绝策略。
- 当线程数到最大且队列也满了，再来任务就会触发拒绝策略。
- 常见有：
- `AbortPolicy`：直接抛异常
- `CallerRunsPolicy`：由调用线程执行
- `DiscardPolicy`：直接丢弃
- `DiscardOldestPolicy`：丢弃队列最老任务

7. 参数之间的执行流程

- 新任务先看核心线程是否满。
- 没满，创建核心线程执行。
- 满了，放进阻塞队列。
- 队列满了，再创建非核心线程。
- 如果也到最大线程数了，就执行拒绝策略。

面试怎么答：

- 线程池核心参数重点记核心线程数、最大线程数、存活时间、任务队列和拒绝策略。
- 任务执行流程是：先核心线程，再队列，再非核心线程，最后拒绝策略。

高频考点：

- 为什么不建议使用 `Executors` 默认线程池
- 线程池参数怎么配置
- 常见阻塞队列区别
- 拒绝策略实际怎么选

扣分点：

- 只会背参数名，不会讲执行流程
- 说不清队列和最大线程数谁先生效
- 不知道拒绝策略触发条件

##### 追问 15
问题：CAS 为什么会有自旋开销

回答：
核心结论：

CAS 失败后通常不会立刻阻塞线程，而是不断重试。

这个不断重试的过程就叫自旋。

如果竞争激烈，线程会反复比较、反复失败、反复重试，这就会持续消耗 CPU。

1. 为什么要自旋

- CAS 的核心思路是无锁更新。
- 更新失败时，说明共享变量被别的线程改过了。
- 这时候通常不会挂起线程。
- 而是马上重新读取，再继续 CAS。

2. 自旋为什么有开销

- 因为线程虽然没阻塞，但它一直在运行。
- 会不断占用 CPU 做比较和重试。
- 如果短时间一直抢不到，CPU 就被白白消耗了。

3. 什么时候问题明显

- 线程很多。
- 竞争同一个共享变量很激烈。
- 或者临界区冲突很频繁。
- 这时 CAS 失败率会很高，自旋开销就明显。

4. 怎么理解它的优缺点

- 竞争不激烈时，CAS 很高效。
- 因为省掉了线程切换和阻塞唤醒成本。
- 竞争很激烈时，自旋反而可能不如加锁。

面试怎么答：

- CAS 失败后一般会自旋重试，不会马上阻塞线程。
- 自旋期间线程会一直占用 CPU。
- 所以高并发冲突严重时，会产生明显的自旋开销。

扣分点：

- 只会说 CAS 快，不知道它也有代价
- 不知道自旋本质是“忙等”
- 不知道竞争激烈时自旋可能更浪费 CPU

### 问题 001：JVM 的内存模型和垃圾回收机制

#### 时间
2026-03-26

#### 问题
谈谈 JVM 的内存模型和垃圾回收机制。

#### 回答
一句话回答：

JVM 内存模型可以理解为“对象放哪、线程怎么访问”。

垃圾回收机制可以理解为“哪些对象该回收、什么时候回收、怎么回收”。

面试回答：

1. JVM 内存模型（面试常指运行时数据区）

- 线程私有：
- `程序计数器`
- `虚拟机栈`
- `本地方法栈`

- 线程共享：
- `堆`
- `方法区（元空间）`

- 堆是对象实例和数组的主要存放区域，也是 GC 的核心区域。
- 方法区主要放类元数据、常量、静态变量等。
- 栈里主要是方法调用栈帧、局部变量、操作数栈。

2. 对象分配和代际思想

- 大部分新对象先进入新生代（Eden）。
- 新生代经过多次 Minor GC 仍存活的对象会晋升到老年代。
- 这样做是因为“多数对象朝生夕死”，分代回收效率更高。

3. 怎么判断对象是否可回收

- 主流用“可达性分析”。
- 从 GC Roots 出发，找可达对象。
- 不可达对象才有机会被回收。

- 常见 GC Roots：
- 栈中引用的对象
- 静态变量引用对象
- 常量引用对象
- JNI 引用对象

4. 垃圾回收机制（按区域看）

- 新生代常用“复制算法”。
- 把存活对象复制到另一块区域，清理整块旧区域，速度快。

- 老年代常用“标记-清除”或“标记-整理”。
- 标记-清除会有内存碎片。
- 标记-整理会做压缩，碎片更少但移动对象成本更高。

5. 常见 GC 类型

- Minor GC：回收新生代。
- Major GC / Old GC：回收老年代。
- Full GC：通常回收整个堆和方法区，停顿时间一般更长，应尽量减少。

6. 常见垃圾收集器（面试常问）

- `Serial`：单线程，简单，适合小堆。
- `ParNew` / `Parallel Scavenge`：新生代并行回收。
- `CMS`：以低停顿为目标，老年代并发回收，但有碎片问题（新版本已弱化）。
- `G1`：面向服务端常用，按 Region 管理内存，兼顾吞吐和停顿，可预测停顿。

7. 面试中的实战表达

- 线上关注的不只是“用了什么收集器”。
- 更关键是：GC 频率、停顿时间、Full GC 次数、堆内存分配是否合理。
- 常见优化手段是调堆大小、调新生代比例、选合适收集器、排查内存泄漏。

高频追问：

- JVM 内存模型和 Java 内存模型（JMM）区别
- 对象什么时候进入老年代
- 什么情况下会触发 Full GC
- CMS 和 G1 区别
- 如何排查频繁 Full GC

扣分点：

- 把 JVM 内存模型和 JMM 混为一谈
- 只背“堆栈方法区”，讲不出 GC 判断和回收算法
- 说不清 Minor GC、Major GC、Full GC 区别
- 只会背收集器名字，不会说使用场景

#### 关键词
JVM, 运行时数据区, 堆, 栈, 元空间, 可达性分析, GC, G1

#### 追问记录

##### 追问 1
问题：JVM 内存模型 vs JMM 区别

回答：
核心结论：

JVM 内存模型（面试常说）是“运行时内存分区”。

JMM 是“多线程下共享变量的可见性、原子性、有序性规则”。

两者不是一个维度。

1. JVM 内存模型（运行时数据区）

- 关注内存怎么划分：
- 堆、栈、方法区、程序计数器、本地方法栈。
- 重点是对象放在哪、哪块会 GC。

2. JMM（Java Memory Model）

- 关注线程之间怎么安全读写共享变量。
- 重点是可见性、原子性、有序性。
- 关键概念有：`happens-before`、主内存/工作内存、指令重排。

3. 一句话区分

- JVM 内存模型：内存“区域划分”问题。
- JMM：线程“并发访问规则”问题。

扣分点：

- 把两者当同一个概念
- 说 JVM 内存模型时只讲 `volatile`、`synchronized`

##### 追问 2
问题：Minor / Major / Full GC 区别

回答：
核心结论：

- Minor GC：主要回收新生代。
- Major GC（Old GC）：主要回收老年代。
- Full GC：通常回收整个堆（新生代+老年代）以及方法区，停顿一般最长。

1. Minor GC

- 触发频率高。
- 回收快，停顿相对短。
- 常见触发：Eden 区满。

2. Major GC / Old GC

- 主要针对老年代。
- 频率通常低于 Minor GC。
- 停顿时间一般比 Minor GC 长。

3. Full GC

- 范围最大，代价最高。
- 一般会带来明显 STW 停顿。
- 线上要重点关注 Full GC 次数和耗时。

扣分点：

- 把 Major GC 和 Full GC 完全等同
- 只会背名词，不知道哪个停顿更敏感

##### 追问 3
问题：Full GC 常见触发条件

回答：
核心结论：

Full GC 常见触发本质就三类：老年代压力大、元空间压力大、显式触发。

1. 老年代空间不足

- 对象晋升到老年代失败。
- 老年代没有足够连续空间。
- 大对象直接进入老年代导致空间紧张。

2. 元空间不足

- 动态生成大量类（代理类、反射、热部署场景）。
- 元空间逼近上限时可能触发 Full GC 尝试回收类元数据。

3. 显式调用

- 代码里调用 `System.gc()`。
- 默认可能触发 Full GC（可通过参数控制策略）。

4. 担保失败/分配失败相关

- 年轻代回收后仍无法满足分配或晋升需求。
- JVM 可能转而触发 Full GC。

扣分点：

- 只说“内存不够会 Full GC”，太泛
- 忽略元空间和 `System.gc()` 场景

##### 追问 4
问题：CMS 和 G1 区别

回答：
核心结论：

CMS 目标是低停顿，但会产生碎片，调优复杂。

G1 通过 Region + 增量回收控制停顿，更适合大堆和现代服务端场景。

1. 内存组织方式

- CMS 基于传统分代模型（新生代/老年代）。
- G1 把堆切成多个 Region，不再是固定连续的新老代边界。

2. 回收思路

- CMS：并发标记清除，低停顿，但会产生内存碎片。
- G1：整体标记整理、局部复制回收，碎片问题更可控。

3. 停顿可控性

- CMS 停顿时间不够可预测，容易受碎片和并发失败影响。
- G1 支持按停顿目标回收，停顿可预测性更好。

4. Full GC 风险

- CMS 在并发模式失败时可能退化到 Serial Old，停顿很长。
- G1 也可能 Full GC，但整体对大堆场景更友好。

5. 选型结论

- 现代 Java 服务端，默认优先考虑 G1（或更新收集器）。
- CMS 了解原理即可，面试重点是它的低停顿目标和碎片缺陷。

扣分点：

- 只说 G1 比 CMS 新
- 说不清 CMS 的碎片问题和并发失败风险

##### 追问 5
问题：线上如何排查频繁 Full GC

回答：
核心结论：

排查频繁 Full GC 要先看“现象”，再判定“是内存泄漏、参数不合理，还是业务流量突增”。

建议按固定步骤走。

1. 先看 GC 日志

- 看 Full GC 频率、单次耗时、回收前后堆占用变化。
- 重点看“回收后是否明显下降”。
- 如果回收后仍很高，优先怀疑内存泄漏或长生命周期对象堆积。

2. 看堆内存与代际分布

- 关注新生代、老年代、元空间占用趋势。
- 判断是年轻代太小导致晋升压力，还是老年代本身装不下。

3. 抓堆快照定位大对象和引用链

- 用 `jmap` 导出堆快照，`MAT` 分析。
- 看大对象类型、对象数量、Retained Size、GC Roots 引用链。
- 找是否有集合缓存不释放、ThreadLocal 泄漏、静态集合持有对象等问题。

4. 看代码和配置

- 是否有不合理缓存策略（只增不删）。
- 是否有频繁创建大对象。
- 是否有动态代理/类加载导致元空间上涨。
- 是否错误调用 `System.gc()`。

5. 看 JVM 参数是否合理

- 堆大小是否过小。
- 新生代比例是否导致过早晋升。
- 元空间上限是否过低。
- 收集器是否适配当前业务负载。

6. 给优化动作

- 调整堆和代际参数，降低晋升压力。
- 优化对象生命周期和缓存淘汰策略。
- 降低大对象分配峰值。
- 必要时升级收集器策略并做压测验证。

面试怎么答：

- 我会先看 GC 日志确认 Full GC 的频率和回收效果。
- 如果回收后占用仍高，优先查内存泄漏，抓堆快照看大对象和引用链。
- 再结合业务代码检查缓存、ThreadLocal、静态集合等问题。
- 同时评估 JVM 参数和收集器配置是否合理，最后用压测验证优化效果。

高频考点：

- 如何判断是参数问题还是内存泄漏
- 堆快照看哪些指标
- 频繁 Full GC 的常见业务代码原因

扣分点：

- 只会说“加大堆内存”
- 不看日志就直接调参数
- 不会用堆快照定位引用链

##### 追问 6
问题：JVM 内存模型 vs JMM 区别 / Minor-Major-Full GC 区别 / Full GC 触发条件 / CMS 和 G1 区别 / 线上排查频繁 Full GC

回答：
本轮为同主题复盘，结论与追问 1-5 一致：

- JVM 内存模型（面试常说）偏运行时内存分区；JMM 偏并发访问规则。
- Minor 回收新生代；Major 主要回收老年代；Full 通常是全堆+方法区，停顿最敏感。
- Full GC 常见触发：老年代不足、元空间不足、晋升失败、`System.gc()`、收集器退化。
- CMS 低停顿但有碎片和并发失败风险；G1 Region 化、停顿可预测性更好，现代服务端更常用。
- 线上排查要先看 GC 日志和监控，再做 heap dump 定位引用链，最后再改代码和 JVM 参数并验证。

### 问题 001：什么是 MySQL 索引？为什么索引能提升查询性能？
#### 时间
2026-03-26

#### 问题
什么是 MySQL 索引？为什么索引能提升查询性能？

#### 回答
索引本质是“有序的数据结构”，最常见是 B+Tree。没有索引时，MySQL 往往要全表扫描；有索引后，可以快速定位到目标数据所在范围，显著减少扫描行数和随机 I/O。
- 索引提升性能的核心不是“更快读取磁盘”，而是“少读很多无关数据”。
- 索引特别适合 `where`、`join`、`order by`、`group by` 场景。
- 索引有代价：写入要维护索引、占用存储空间、也会增加 Buffer Pool 压力。
- 面试里要强调“索引是以空间换时间，且不是越多越好”。

#### 关键词
MySQL, 索引, B+Tree, 全表扫描, 空间换时间

### 问题 002：为什么 InnoDB 选 B+Tree 作为主要索引结构，而不是红黑树或 Hash？
#### 时间
2026-03-26

#### 问题
为什么 InnoDB 选 B+Tree 作为主要索引结构，而不是红黑树或 Hash？

#### 回答
B+Tree 非常适合磁盘和范围查询。它的节点可容纳大量 key，树高低，单次查询磁盘访问次数少；叶子节点有序且可链式遍历，对范围查和排序天然友好。
- 红黑树层高更高，磁盘 I/O 次数通常更多。
- Hash 适合等值查，不适合范围查，也不支持有序遍历。
- B+Tree 非叶子节点只存 key 和指针，单页可放更多分支，整体更扁平。
- InnoDB 与页结构结合后，B+Tree 在 OLTP 场景综合表现更稳。

#### 关键词
B+Tree, 红黑树, Hash, 范围查询, 磁盘 I/O

### 问题 003：聚簇索引和二级索引的区别是什么？
#### 时间
2026-03-26

#### 问题
聚簇索引和二级索引的区别是什么？

#### 回答
InnoDB 的主键索引是聚簇索引，叶子节点直接存整行数据；二级索引叶子节点存“索引列 + 主键值”。
- 通过二级索引查整行时，通常要先查到主键，再回主键索引取整行，这就是回表。
- 聚簇索引按主键顺序组织数据，主键设计会影响数据物理组织。
- 二级索引过多会拖慢写入，因为每次写都要维护多个 B+Tree。
- 面试要点：InnoDB 只有一个聚簇索引，但可以有多个二级索引。

聚簇索引, 二级索引, 回表, InnoDB, 主键

### 问题 004：什么是回表？如何减少回表？
#### 时间
2026-03-26

#### 问题
什么是回表？如何减少回表？

#### 回答
回表指先走二级索引拿到主键，再去聚簇索引取完整行数据的过程。回表会增加随机 I/O 和 CPU 比较成本。

- 对高频 SQL 优先优化回表成本，而不是盲目追求“走了索引就行”。
- 可通过 `EXPLAIN` 观察 `Extra` 是否出现 `Using index` 判断覆盖情况。

联合索引最左前缀原则怎么理解？

### 问题 012：undo log、redo log、binlog 的区别是什么？
#### 时间

#### 问题
undo log、redo log、binlog 的区别是什么？

### 问题 015：什么是 next-key lock？它为什么能避免幻读？
#### 时间

#### 问题
什么是 next-key lock？它为什么能避免幻读？

next-key lock = 记录锁 + 间隙锁，锁住“记录本身及其前后区间”，阻止其他事务在区间内插入新记录。

### 问题 041：Buffer Pool 的作用是什么？
#### 时间
2026-03-26

#### 问题
Buffer Pool 的作用是什么？

#### 回答
Buffer Pool 是 InnoDB 的内存缓存池，用来缓存数据页和索引页，减少磁盘 I/O。
- 读请求优先命中内存页，命中率越高延迟越低。
- 写操作通常先改内存页，再异步刷盘，提升吞吐。
- Buffer Pool 过小会导致频繁淘汰与磁盘抖动。

### 问题 017：AOF 重写（rewrite）是什么？
#### 时间
2026-03-26

#### 问题
AOF 重写（rewrite）是什么？

#### 回答
AOF rewrite 会把历史命令压缩为“恢复当前数据所需的最小命令集”，减少 AOF 文件膨胀。
- 例如多次 `INCR` 可重写成一次 `SET` 最终值。
- rewrite 不阻塞主流程执行，采用子进程 + 增量重放方式。
- 有助于加快重启恢复并降低磁盘占用。
