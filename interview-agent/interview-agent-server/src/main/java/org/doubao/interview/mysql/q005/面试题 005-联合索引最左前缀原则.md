## 🎯 核心知识点

### 一、什么是联合索引？

#### 定义
在多个列上创建的索引，如 `(a, b, c)`。

#### B+Tree 结构
```
【排序规则】
1. 先按 a 排序
2. a 相同的情况下，按 b 排序
3. a,b 都相同的情况下，按 c 排序

【示例数据】
(1,25,5000) → 主键列表
(1,25,6000) → 主键列表
(1,28,5500) → 主键列表
(1,30,7000) → 主键列表
(2,25,5000) → 主键列表
(2,26,5500) → 主键列表
(2,30,8000) → 主键列表
(3,25,6000) → 主键列表
(3,28,7000) → 主键列表
(3,30,9000) → 主键列表
```

---

### 二、什么是最左前缀原则？

#### 定义
联合索引 `(a,b,c)` 可以被 `a`、`a,b`、`a,b,c` 这样的前缀匹配高效利用，但不能直接高效利用 `b`、`c` 开头的条件。

#### 本质原因
B+Tree 按最左列优先排序，后续列在同值区间内有序。

#### 可视化演示

```

║   联合索引结构：idx_a_b_c              ║
╚════════════════════════════════════════╝

【B+Tree 叶子节点】(a, b, c) → 主键列表
┌─────────────────────────────────────┐
│ ( 1,25,5000) → [1831932724]
│ ( 1,25,6000) → [1023892928]
│ ( 1,28,5500) → [558638686]
│ ( 1,30,7000) → [1149319664]
│ ( 2,25,5000) → [2093631819]
│ ( 2,26,5500) → [2074407503]
│ ( 2,30,8000) → [999966131]
│ ( 3,25,6000) → [1989780873]
│ ( 3,28,7000) → [1480010240]
│ ( 3,30,9000) → [81628611]
│ ... (共 10 项)
└─────────────────────────────────────┘

【排序规则】
  1. 先按 a 排序
  2. a 相同的情况下，按 b 排序
  3. a,b 都相同的情况下，按 c 排序

【可利用的前缀】
  ✅ (a) - 第 1 列
  ✅ (a,b) - 前 2 列
  ✅ (a,b,c) - 全部 3 列
  ❌ (b) - 跳过最左列，不可用
  ❌ (c) - 跳过最左两列，不可用
```

## 💡 面试要点

### 必背知识点

1. **最左前缀原则的本质是 B+Tree 的排序规则**
   - 联合索引按最左列优先排序
   - 后续列在同值区间内有序
   - 只能从左往右依次使用

2. **可以利用 (a)、(a,b)、(a,b,c) 作为前缀**
   - 连续的左侧列都可以使用
   - 不要求所有列都用上

3. **跳过最左列会导致索引失效（全扫描）**
   - 如 `(b,c)` 或 `(c)` 开头的查询
   - 无法利用索引的有序性

4. **范围查询会阻断后续列的使用**
   - 如 `a=1 AND b>25`，c 列无法使用
   - 因为 b 列范围查询后，c 列无序

5. **设计索引时要把过滤性强的列放前面**
   - 区分度高的列优先
   - 等值匹配的列优先于范围查询

## 🎯 索引设计原则

### 原则 1：过滤性强、区分度高的列放前面

```sql
-- 场景：部门 ID 区分度高（10 个部门），年龄区分度低（25-35 岁）
-- ✅ 推荐：把区分度高的放前面
CREATE INDEX idx_dept_age ON employees(dept_id, age);

-- ❌ 不推荐：区分度低的放前面
CREATE INDEX idx_age_dept ON employees(age, dept_id);
```

### 原则 2：等值匹配的列优先于范围查询的列

```sql
-- 场景：WHERE dept_id=? AND salary>?
-- ✅ 推荐：等值匹配的列放前面
CREATE INDEX idx_dept_salary ON employees(dept_id, salary);

-- ❌ 不推荐：范围查询的列放前面
CREATE INDEX idx_salary_dept ON employees(salary, dept_id);
```

### 原则 3：高频查询条件优先考虑

```sql
-- 场景：80% 的查询都包含 dept_id
-- ✅ 推荐：把高频列放前面
CREATE INDEX idx_dept_status ON employees(dept_id, status);
```

### 原则 4：考虑覆盖索引，减少回表

```sql
-- 场景：经常查询 SELECT id, dept_id, age WHERE dept_id=?
-- ✅ 推荐：包含所有查询列
CREATE INDEX idx_dept_age_id ON employees(dept_id, age, id);
-- 可以直接从索引返回，无需回表
```

## 🔍 经典面试题

### Q1: 什么是联合索引的最左前缀原则？

**A**: 
- **定义**：联合索引 `(a,b,c)` 只能从最左列开始匹配
- **可用前缀**：`(a)`、`(a,b)`、`(a,b,c)`
- **不可用**：`(b)`、`(c)`、`(b,c)`
- **本质**：B+Tree 按最左列优先排序

### Q2: 为什么跳过最左列索引会失效？

**A**:
- 联合索引按 `(a,b,c)` 的顺序排序
- 先按 a 排序，再按 b 排序，最后按 c 排序
- 如果跳过 a 直接查 b，b 在全局是无序的
- 无法利用二分查找，只能全扫描

### Q3: 范围查询对联合索引有什么影响？

**A**:
- 范围查询会阻断后续列的使用
- 如 `WHERE a=1 AND b>25 AND c=100`
- a 和 b 可以使用索引
- c 列无法使用（因为 b 范围查询后，c 无序）

### Q4: 如何设计一个高效的联合索引？

**A**:
1. 过滤性强、区分度高的列放前面
2. 等值匹配的列优先于范围查询的列
3. 高频查询条件优先考虑
4. 尽量包含查询列，实现覆盖索引

### Q5: 最左前缀是"可利用前缀"，不等于"后面列完全没用"，如何理解？

**A**:
- **可利用前缀**：可以从任意左侧列开始使用
- **ICP 优化**：即使不能直接查找，也可能用于过滤
- **覆盖索引**：后面的列可能避免回表
- **索引下推**：MySQL 5.6+ 支持在索引层过滤

## 📝 核心要点总结

### 一句话答案

**联合索引 (a,b,c) 按最左列优先排序，可以被 a、a,b、a,b,c 这样连续的前缀匹配高效利用，但不能跳过最左列直接使用后面的列。**

### 三个关键点

1. **排序规则**
   - 先按最左列 a 排序
   - a 相同的情况下按 b 排序
   - a,b 都相同的情况下按 c 排序

2. **可利用前缀**
   - ✅ (a) - 第 1 列
   - ✅ (a,b) - 前 2 列
   - ✅ (a,b,c) - 全部 3 列
   - ❌ (b) - 跳过最左列，不可用
   - ❌ (c) - 跳过最左两列，不可用

3. **设计原则**
   - 过滤性强的列放前面
   - 等值匹配优先于范围查询
   - 高频查询条件优先考虑

### 记忆口诀

```
a 排完 b 接着排，c 在最后跟着来
能用 abc 前三列，也能只用 ab 配
单独用 a 也可以，跳过 a 就拜拜
范围查询会阻断，后面兄弟用不来
设计要把强的放，高频等值排前排
```
