## 🎯 核心知识点

### 四种隔离级别（SQL 标准）

```
┌─────────────┬──────────┬──────────────┬──────────┐
│ 隔离级别     │ 脏读     │ 不可重复读   │ 幻读     │
├─────────────┼──────────┼──────────────┼──────────┤
│ 读未提交     │ ✅ 可能   │ ✅ 可能      │ ✅ 可能   │
│ 读已提交     │ ❌ 避免   │ ✅ 可能      │ ✅ 可能   │
│ 可重复读     │ ❌ 避免   │ ❌ 避免      │ ⚠️ 大部分  │
│ 串行化       │ ❌ 避免   │ ❌ 避免      │ ❌ 避免   │
└─────────────┴──────────┴──────────────┴──────────┘
```

### 一、读未提交（Read Uncommitted）

#### 定义
最低的隔离级别，允许读取未提交的数据。

#### 并发问题
- **脏读** ✅：读到其他事务未提交的修改
- **不可重复读** ✅：同一查询可能读到不同数据
- **幻读** ✅：同一查询可能读到不同行数

#### 演示示例

```sql
-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- 事务 A：开始并修改（未提交）
START TRANSACTION;
UPDATE accounts SET balance = 800 WHERE id = 1;
-- 未提交

-- 事务 B：读取（能看到未提交的数据）
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 800（未提交的值）

-- 事务 A：回滚
ROLLBACK;

-- 事务 B：再次读取
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 1000（原始值）
-- ⚠️  事务 B 之前读到的 800 就是脏数据！
```

**执行过程**：
```
【设置隔离级别】读未提交

【事务 A】开始并修改数据

╔════════════════════════════════════════╗
║   开始事务 TX-1（隔离级别：读未提交）   ║
╚════════════════════════════════════════╝

[UPDATE] 更新 Row 1
  旧值：{balance=1000, name=张三}
  新值：{balance=800}
  ✅ 更新成功
  ⚠️  事务 A 未提交！

【事务 B】读取数据

╔════════════════════════════════════════╗
║   开始事务 TX-2（隔离级别：读未提交）   ║
╚════════════════════════════════════════╝

[SELECT] 查询 Row 1
  当前事务 ID: 2
  隔离级别：读未提交
  ✅ 返回可见版本：Row{id=1, data={balance=800}, txId=1, committed=false}
  ⚠️  事务 B 读到了事务 A 未提交的数据（脏读）！

【事务 A】回滚
  → 如果事务 A 回滚，事务 B 读到的就是脏数据

【并发问题总结】
  ❌ 脏读：读到未提交的数据
  ❌ 不可重复读：同一查询可能读到不同数据
  ❌ 幻读：同一查询可能读到不同行数
```

**适用场景**：
- 统计类查询（不要求精确）
- 只读数据分析
- 对性能要求极高，能容忍脏数据

### 二、读已提交（Read Committed, RC）

#### 定义
只能读取到已经提交的事务所做的修改。

#### 并发问题
- **脏读** ❌：避免（只读已提交）
- **不可重复读** ✅：可能发生
- **幻读** ✅：可能发生

#### MVCC 机制
- **Read View 策略**：每次读取都创建新的 Read View
- **可见性规则**：只能看到已提交的版本

#### 演示示例

```sql
-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 事务 A：第一次读取
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 1000

-- 事务 B：修改并提交
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;

-- 事务 A：第二次读取（同一事务内）
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 800（不同的值！）
-- ⚠️  不可重复读！
```

**执行过程**：
```
【设置隔离级别】读已提交 (RC)

【事务 A】第一次读取

╔════════════════════════════════════════╗
║   开始事务 TX-1（隔离级别：读已提交）   ║
╚════════════════════════════════════════╝

📖 创建 Read View: ReadView{creator=1, active=[1]}

[SELECT] 查询 Row 1
  ✅ 返回可见版本：Row{id=1, data={balance=1000}, committed=true}

【事务 B】修改并提交

╔════════════════════════════════════════╗
║   开始事务 TX-2（隔离级别：读已提交）   ║
╚════════════════════════════════════════╝

[UPDATE] 更新 Row 1
  旧值：{balance=1000}
  新值：{balance=800}
  ✅ 更新成功

【提交事务 TX-2】
  ℹ️  RC 级别：清除 Read View（下次读取时重新创建）
  ✅ 事务 TX-2 提交成功

【事务 A】第二次读取（同一事务内）

[SELECT] 查询 Row 1
  ✅ 返回可见版本：Row{id=1, data={balance=800}, committed=true}
  ⚠️  同一事务内，两次读取结果不同（不可重复读）！

【并发问题总结】
  ✅ 避免脏读：只读已提交的数据
  ❌ 不可重复读：同一事务内可能读到不同数据
  ❌ 幻读：仍可能发生
```

**适用场景**：
- Oracle 默认隔离级别
- 大多数业务系统
- 对并发一致性要求不是特别严格

### 三、可重复读（Repeatable Read, RR）

#### 定义
确保在同一个事务内的多次读取同样的记录，会看到同样的数据。

#### 并发问题
- **脏读** ❌：避免
- **不可重复读** ❌：避免
- **幻读** ⚠️：大部分避免（InnoDB 使用 Next-Key Lock）

#### MVCC 机制
- **Read View 策略**：事务开始时创建 Read View，保持不变
- **可见性规则**：整个事务看到同一版本

#### InnoDB 特性
- **MySQL InnoDB 默认隔离级别**
- **Next-Key Lock**：行锁 + 间隙锁，抑制幻读
- **MVCC 优秀实现**：RR 级别下仍能保持高并发

#### 演示示例

```sql
-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 事务 A：第一次读取
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 1000

-- 事务 B：修改并提交
UPDATE accounts SET balance = 800 WHERE id = 1;
COMMIT;

-- 事务 A：第二次读取（同一事务内）
SELECT * FROM accounts WHERE id = 1;
-- 返回：balance = 1000（相同的值！）
-- ✅ 可重复读！
```

**执行过程**：
```
【设置隔离级别】可重复读 (RR)

【事务 A】第一次读取

╔════════════════════════════════════════╗
║   开始事务 TX-1（隔离级别：可重复读）   ║
╚════════════════════════════════════════╝

📖 创建 Read View: ReadView{creator=1, active=[1]}

[SELECT] 查询 Row 1
  ✅ 返回可见版本：Row{id=1, data={balance=1000}, committed=true}

【事务 B】修改并提交

╔════════════════════════════════════════╗
║   开始事务 TX-2（隔离级别：可重复读）   ║
╚════════════════════════════════════════╝

[UPDATE] 更新 Row 1
  旧值：{balance=1000}
  新值：{balance=800}
  ✅ 更新成功

【提交事务 TX-2】
  ℹ️  RR 级别：保持 Read View（整个事务看到同一版本）
  ✅ 事务 TX-2 提交成功

【事务 A】第二次读取（同一事务内）

[SELECT] 查询 Row 1
  ✅ 返回可见版本：Row{id=1, data={balance=1000}, committed=true}
  ✅ 同一事务内，两次读取结果相同（可重复读）！
  ℹ️  RR 级别：Read View 在事务开始时创建，保持不变

【并发问题总结】
  ✅ 避免脏读：只读已提交的数据
  ✅ 避免不可重复读：同一事务内看到相同数据
  ⚠️  大部分避免幻读：InnoDB 使用 Next-Key Lock
```

**适用场景**：
- **MySQL InnoDB 默认隔离级别**
- 复杂业务逻辑
- 对数据一致性要求较高

### 四、串行化（Serializable）

#### 定义
最高的隔离级别，强制事务串行执行，就像按顺序排队一样。

#### 并发问题
- **脏读** ❌：避免
- **不可重复读** ❌：避免
- **幻读** ❌：避免

#### 实现机制
- **强锁机制**：所有读写操作都加锁
- **串行执行**：事务一个接一个执行
- **性能最低**：并发能力最差

#### 演示示例

```sql
-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 事务 A：读取（加共享锁）
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1;

-- 事务 B：尝试修改（被阻塞）
UPDATE accounts SET balance = 800 WHERE id = 1;
-- ⏸️  等待事务 A 提交...

-- 事务 A：提交
COMMIT;

-- 事务 B：才能执行
```

**适用场景**：
- 对数据一致性要求极高
- 并发量低的场景
- 金融核心系统

## 💡 面试要点

### 必背知识点

1. **MySQL InnoDB 默认隔离级别是 RR（可重复读）**
   - 不是 RC！这是常见误区
   - Oracle 默认是 RC

2. **RC 和 RR 都使用 MVCC，但 Read View 保持策略不同**
   - RC：每次读取都创建新 Read View
   - RR：事务开始时创建 Read View，保持不变

3. **InnoDB 在 RR 下使用 Next-Key Lock 抑制幻读**
   - 行锁 + 间隙锁
   - 防止其他事务插入新行

4. **隔离级别越高，并发能力通常越弱**
   - 读未提交：⭐⭐⭐⭐⭐ 最高
   - 读已提交：⭐⭐⭐⭐ 较高
   - 可重复读：⭐⭐⭐ 中等
   - 串行化：⭐ 最低

5. **三种并发问题的定义**
   - 脏读：读到未提交的数据
   - 不可重复读：同一事务内读到不同数据
   - 幻读：同一查询读到不同行数

## 🎯 深入理解

### MVCC 实现原理

```
【版本链】
Row 1: 
  version1: balance=1000 (tx_id=1, committed=true)
    ↓ (undo log pointer)
  version2: balance=800 (tx_id=2, committed=false)

【Read View】
- creatorTxId: 创建者事务 ID
- minActiveTxId: 最小活跃事务 ID
- activeTxIds: 活跃事务列表

【可见性判断（RC/RR）】
1. 如果版本已提交 → 可见
2. 如果版本创建者是自己 → 可见
3. 如果版本未提交且不是自己 → 不可见
```

### RC vs RR 对比

```
【RC（读已提交）】
• 每次 SELECT 都创建新的 Read View
• 所以能看到其他事务新提交的修改
• 导致不可重复读

【RR（可重复读）】
• 事务开始时创建 Read View，保持不变
• 只能看到事务开始时的已提交版本
• 保证可重复读
```

### Next-Key Lock

```
【组成】
Next-Key Lock = Record Lock（行锁） + Gap Lock（间隙锁）

【作用】
• 锁定记录本身
• 锁定记录之间的间隙
• 防止其他事务插入新行（抑制幻读）

【示例】
索引：(1, 5, 10)
锁定范围：(-∞, 1], (1, 5], (5, 10], (10, +∞)
其他事务无法在任何间隙中插入新记录
```

## 🔍 经典面试题

### Q1: MySQL 的默认隔离级别是什么？

**A**: 
- **InnoDB 引擎**：可重复读（Repeatable Read, RR）
- 可以通过 `SELECT @@transaction_isolation;` 查看
- 注意：不是读已提交（RC），这是常见误区

### Q2: 什么是脏读、不可重复读、幻读？

**A**:
- **脏读**：读到其他事务未提交的修改
- **不可重复读**：同一事务内，多次读取同一数据得到不同结果
- **幻读**：同一事务内，多次查询返回的行数不同

### Q3: RC 和 RR 的区别是什么？

**A**:
- **RC（读已提交）**：
  - 每次读取都创建新的 Read View
  - 避免脏读，但可能不可重复读
  - Oracle 默认级别
  
- **RR（可重复读）**：
  - 事务开始时创建 Read View，保持不变
  - 避免脏读和不可重复读
  - MySQL InnoDB 默认级别

### Q4: MySQL 如何解决幻读问题？

**A**:
- **快照读**（普通 SELECT）：通过 MVCC 解决
- **当前读**（SELECT ... FOR UPDATE）：通过 Next-Key Lock 解决
  - Next-Key Lock = 行锁 + 间隙锁
  - 锁定记录本身和记录间的间隙
  - 防止其他事务插入新行

### Q5: 为什么 MySQL 选择 RR 作为默认隔离级别？

**A**:
- **历史兼容性**：早期版本就使用 RR
- **MVCC 实现优秀**：RR 下仍能保持高并发
- **业务需求**：避免不可重复读，适合复杂业务
- **抑制幻读**：通过 Next-Key Lock 大部分避免幻读

## 📝 核心要点总结

### 一句话答案

**MySQL 支持四种隔离级别：读未提交（可能脏读、不可重复读、幻读）、读已提交（避免脏读但仍可能不可重复读与幻读）、可重复读（InnoDB 默认，避免脏读和不可重复读，配合 Next-Key Lock 抑制大部分幻读）、串行化（最安全但并发最低）。**

### 三个关键点

1. **隔离级别对照表**
   - 读未提交：三种问题都可能
   - 读已提交：避免脏读
   - 可重复读：避免脏读 + 不可重复读
   - 串行化：全部避免

2. **MVCC 机制**
   - RC：每次读取都创建新 Read View
   - RR：事务开始时创建 Read View，保持不变

3. **性能对比**
   - 隔离级别越高，并发能力越弱
   - MySQL InnoDB 默认 RR（平衡一致性和并发）

### 记忆口诀

