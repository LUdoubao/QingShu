## 🎯 核心知识点

### 一、什么是索引失效？

#### 定义
查询无法利用索引的快速查找能力，退化为全表扫描 O(n)，性能严重下降。

#### 判断方法
使用 EXPLAIN 查看执行计划：
- `key = NULL` → 未使用索引
- `type = ALL` → 全表扫描
- `rows = 大量` → 扫描行数多

---

### 二、常见失效场景详解

#### 场景 1：隐式类型转换导致索引失效 ❌

**错误写法**：
```sql
SELECT * FROM users WHERE phone = 13800138000;
-- phone 是 varchar 类型，却用数字比较
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ALL（全表扫描）          │
│ key         │ NULL（无索引）           │
│ rows        │ 10                       │
│ Extra       │ Using where              │
└─────────────┴──────────────────────────┘

⚠️  索引失效，建议优化！
```

**正确写法**：
```sql
SELECT * FROM users WHERE phone = '13800138000';
-- 使用字符串常量，加引号
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ref / range              │
│ key         │ idx_phone                │
│ rows        │ 少量                     │
│ Extra       │ Using index condition    │
└─────────────┴──────────────────────────┘

✅ 使用索引查找 O(log_N n)
```

**原理分析**：
- MySQL 会将 phone 列的值转换为数字进行比较
- 相当于对索引列做了函数操作：`CAST(phone AS SIGNED)`
- 索引失效，退化为全表扫描

**最佳实践**：
- ✅ 字符串类型要加引号
- ✅ 避免在索引列上进行类型转换

---

#### 场景 2：函数包裹导致索引失效 ❌

**错误写法**：
```sql
SELECT * FROM users WHERE DATE(create_time) = '2024-01-01';
-- 在索引列上使用函数
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ALL（全表扫描）          │
│ key         │ NULL（无索引）           │
│ rows        │ 10                       │
│ Extra       │ Using where              │
└─────────────┴──────────────────────────┘
```

**正确写法**：
```sql
SELECT * FROM users 
WHERE create_time >= '2024-01-01 00:00:00' 
  AND create_time < '2024-01-02 00:00:00';
-- 直接比较，避免函数
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ref / range              │
│ key         │ idx_create_time          │
│ rows        │ 少量                     │
│ Extra       │ Using index condition    │
└─────────────┴──────────────────────────┘
```

**原理分析**：
- `DATE(create_time)` 会对每一行进行计算
- 无法利用索引的有序性
- 退化为全表扫描

**类似场景**：
```sql
❌ WHERE YEAR(create_time) = 2024
❌ WHERE SUBSTR(phone, 1, 3) = '138'
❌ WHERE LOWER(email) = 'test@example.com'
```

**最佳实践**：
- ✅ 使用范围查询代替函数
- ✅ 避免在索引列上进行计算

---

#### 场景 3：前导 % 模糊查询导致索引失效 ❌

**错误写法**：
```sql
SELECT * FROM users WHERE name LIKE '%三%';
-- 前导 % 无法利用索引
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ALL（全表扫描）          │
│ key         │ NULL（无索引）           │
│ rows        │ 10                       │
│ Extra       │ Using where              │
└─────────────┴──────────────────────────┘
```

**正确写法**：
```sql
SELECT * FROM users WHERE name LIKE '张%';
-- 后缀 % 可以利用索引
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   属性      │          值              │
├─────────────┼──────────────────────────┤
│ id          │ 1                        │
│ type        │ ref / range              │
│ key         │ idx_name                 │
│ rows        │ 少量                     │
│ Extra       │ Using index condition    │
└─────────────┴──────────────────────────┘
```

**原理分析**：
- 索引按前缀排序，'张' 开头的在一起
- `%三%` 需要扫描所有记录
- `张%` 可以直接定位到'张'的范围

**最佳实践**：
- ✅ 尽量使用 `'abc%'` 形式
- ❌ 避免使用 `'%abc%'` 或 `'%abc'`
- ⚠️  如果必须用 `'%abc%'`，考虑全文索引

---

#### 场景 4：联合索引不满足最左前缀 ❌

假设有联合索引：`idx_dept_age(dept_id, age)`

**符合最左前缀**：
```sql
✅ WHERE dept_id=1                    → 可以使用索引
✅ WHERE dept_id=1 AND age=25         → 可以使用完整索引
```

**跳过最左列**：
```sql
❌ WHERE age=25                       → 索引失效，全表扫描
```

**原理分析**：
- 联合索引按 `(dept_id, age)` 排序
- 先按 dept_id 排序，再按 age 排序
- 跳过 dept_id 直接查 age，age 是无序的

**最佳实践**：
- ✅ 遵循最左前缀原则
- ✅ 把过滤性强的列放前面

---

#### 场景 5：OR 条件导致索引失效 ❌

**错误写法**：
```sql
SELECT * FROM users 
WHERE phone='13800138000' OR email='test@example.com';
-- phone 有索引，但 email 没有索引
```

**问题分析**：
- phone 有索引，但 email 没有索引
- 优化器可能放弃索引，选择全表扫描

**正确写法 1**：
```sql
SELECT * FROM users 
WHERE phone='13800138000' OR name='张三';
-- phone 和 name 都有索引
-- 可能使用 index_merge 优化
```

**正确写法 2（更好的方式）**：
```sql
SELECT * FROM users WHERE phone='13800138000'
UNION
SELECT * FROM users WHERE email='test@example.com';
-- 分别使用索引，然后合并结果
```

**最佳实践**：
- ✅ OR 连接的条件列都要有索引
- ✅ 或者使用 UNION 代替 OR

---

#### 场景 6：!= 或 <> 导致索引失效 ⚠️

**错误写法**：
```sql
SELECT * FROM users WHERE age != 30;
-- 不等于条件
```

**问题分析**：
- 大部分记录都满足条件
- 优化器可能选择全表扫描

**可能的优化**：
```sql
SELECT * FROM users WHERE age < 30 OR age > 30;
-- 仍然可能全表扫描
-- 但如果数据分布不均，可能使用索引
```

**最佳实践**：
- ⚠️  慎用 `!=` 或 `<>`
- ✅ 考虑业务场景，看是否能转换为其他条件

## 📊 索引失效场景总结

| 场景 | 索引状态 | 性能影响 | 说明 |
|------|---------|---------|------|
| **隐式类型转换** | ❌ 失效 | ⭐ 最差 | 字符串不加引号 |
| **函数包裹索引列** | ❌ 失效 | ⭐ 最差 | DATE()、YEAR() 等 |
| **前导 % 模糊查询** | ❌ 失效 | ⭐ 最差 | LIKE '%abc%' |
| **跳过最左前缀** | ❌ 失效 | ⭐ 最差 | 联合索引违反原则 |
| **OR 连接非索引列** | ❌ 失效 | ⭐ 最差 | 一个无索引就失效 |
| **!= 或 <>** | ⚠️ 可能 | ⭐⭐ 较差 | 取决于数据分布 |
| **IS NULL** | ⚠️ 可能 | ⭐⭐⭐ 一般 | 取决于空值比例 |
| **正常等值匹配** | ✅ 有效 | ⭐⭐⭐⭐⭐ 最优 | 正确使用索引 |

## 💡 面试要点

### 必背知识点

1. **索引列不能参与函数或表达式计算**
   - 函数会破坏索引的有序性
   - 表达式会导致每行计算

2. **避免隐式类型转换（字符串要加引号）**
   - varchar 类型必须加引号
   - 否则会发生类型转换

3. **like 查询避免前导 %**
   - `'abc%'` 可以用索引
   - `'%abc%'` 无法用索引

4. **联合索引遵循最左前缀原则**
   - 只能从左往右依次使用
   - 不能跳过左侧列

5. **OR 条件要谨慎使用**
   - OR 连接的列都要有索引
   - 或者使用 UNION 代替

6. **用 EXPLAIN 判断是否失效**
   - 观察 key 字段是否为 NULL
   - 观察 type 字段是否为 ALL

## 🔍 经典面试题

### Q1: 为什么 `WHERE phone = 13800138000` 会索引失效？

**A**: 
- phone 是 varchar 类型，应该加引号
- 不加引号会触发隐式类型转换
- 相当于 `CAST(phone AS SIGNED) = 13800138000`
- 对索引列做函数操作，索引失效

### Q2: 如何优化 `WHERE DATE(create_time) = '2024-01-01'`？

**A**:
- 使用范围查询代替函数
- 改为 `create_time >= '2024-01-01 00:00:00' AND create_time < '2024-01-02 00:00:00'`
- 这样可以使用 create_time 上的索引

### Q3: LIKE '%abc%' 一定会索引失效吗？

**A**:
- 是的，前导 % 无法利用 B+Tree 的前缀有序性
- 优化方案：
  1. 改用 `'abc%'`（如果业务允许）
  2. 使用全文索引（FULLTEXT）
  3. 使用搜索引擎（Elasticsearch）

### Q4: 如何判断索引是否失效？

**A**:
- 使用 EXPLAIN 查看执行计划
- 观察 key 字段是否为 NULL
- 观察 type 字段是否为 ALL
- 观察 rows 扫描行数
- 不要靠猜，要看执行计划

### Q5: IS NULL 会导致索引失效吗？

**A**:
- 不一定
- 如果索引列允许 NULL，且查询 `WHERE col IS NULL`
- 可以使用索引（特别是 NULL 值较少时）
- 但如果 NULL 值很多，优化器可能选择全表扫描

## 📝 核心要点总结

### 一句话答案

**索引失效的常见场景包括：索引列参与函数或表达式、隐式类型转换、前导 % 模糊查询、联合索引不满足最左前缀、使用 or 导致优化器放弃索引等。判断是否失效要靠 EXPLAIN，而不是猜测。**

### 三个关键点

1. **失效原因**
   - 函数或表达式破坏了索引的有序性
   - 类型转换导致无法直接比较
   - 前导 % 无法利用前缀匹配

2. **判断方法**
   - 使用 EXPLAIN 查看执行计划
   - 观察 key/type/rows 字段
   - 定期分析慢查询日志

3. **优化策略**
   - 避免在索引列上使用函数
   - 字符串类型要加引号
   - like 查询用后缀 %
   - 遵循最左前缀原则
   - OR 改 UNION
