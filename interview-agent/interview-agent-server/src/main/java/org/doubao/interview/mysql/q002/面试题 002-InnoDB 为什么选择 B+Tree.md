# 面试题 002：为什么 InnoDB 选择 B+Tree 作为索引结构？

## 📦 文件说明

### 核心实现类

1. **BPlusTree.java** - B+Tree 简化实现
   - 路径：`question002/index/BPlusTree.java`
   - 多叉树结构，非叶子节点只存索引
   - 所有数据在叶子节点，叶子节点通过指针相连
   - 支持高效的范围查询和有序遍历

2. **RedBlackTree.java** - 红黑树简化实现
   - 路径：`question002/index/RedBlackTree.java`

3. **HashIndex.java** - Hash 索引简化实现
   - 路径：`question002/index/HashIndex.java`
   - 基于 HashMap 实现
   - O(1) 时间复杂度查询
   - 只支持等值查询，不支持范围查

4. **IndexComparisonDemo.java** - 对比演示程序
   - 路径：`question002/demo/IndexComparisonDemo.java`

   - 可视化展示三种索引结构的差异

## 🎯 核心知识点

### 一、B+Tree 的核心优势

#### 1. 磁盘友好（最重要）

```
B+Tree 结构（4 阶）：
         [50]
        /    \
    [25]      [75]
   /   \     /   \
[10,25] [30,50] [60,75] [90]

树高 = 3，一次查询最多 3 次磁盘 I/O
```

**对比红黑树**：
```
红黑树（相同数据量）：
        50(黑)
       /      \
    25(红)    75(红)
   /   \      /   \
10(黑) 30(黑) 60(黑) 90(黑)
  ...
  
树高 = log₂(n)，n=100 万时，树高≈20
需要 20 次磁盘 I/O！
```

**结论**：B+Tree 树高低 3-5 倍，磁盘 I/O 少 3-5 倍

#### 2. 范围查询无敌

```sql
-- 场景：查询年龄在 20-30 岁之间的用户
SELECT * FROM users WHERE age BETWEEN 20 AND 30;
```

**B+Tree 执行过程**：
```
1. 定位到 age=20 的叶子节点（O(log_N n)）
2. 沿着链表向后扫描（O(k)，k 为结果数）
3. 遇到 age>30 时停止

总时间复杂度：O(log_N n + k)
```

**Hash 索引执行过程**：
```
1. 无法使用索引（哈希无序）
2. 全表扫描所有记录
3. 逐行过滤 age BETWEEN 20 AND 30

总时间复杂度：O(n)
```

**性能差距**：100 万数据，B+Tree 快 100 倍！

#### 3. 排序优化

```sql
-- 场景：按年龄排序取前 10 名
SELECT * FROM users ORDER BY age LIMIT 10;
```

**B+Tree**：
- ✅ 叶子节点天然有序
- ✅ 直接顺序扫描前 10 个节点
- ✅ 无需额外排序操作

**Hash 索引**：
- ❌ 数据无序存储
- ❌ 需要全表扫描
- ❌ 需要排序（O(n log n)）

#### 4. 性能稳定

**B+Tree**：
- 所有查询都要到叶子节点
- 不存在最坏情况
- 性能可预测

**红黑树**：
- 可能存在不平衡情况
- 极端情况下退化为链表
- 性能波动大

## 💡 面试高频问题

### Q1: 为什么 B+Tree 比红黑树更适合磁盘存储？

**A**：三个关键原因

1. **树高更低**
   ```
   B+Tree（100 万数据）：log_100(1000000) ≈ 3 层
   红黑树（100 万数据）：log_2(1000000) ≈ 20 层
   
   磁盘 I/O 差距：20/3 ≈ 6.7 倍
   ```

2. **节点利用率高**
   ```
   B+Tree 非叶子节点：只存 key+ 指针（~100 字节/节点）
   红黑树节点：存 key+value+ 颜色 + 左右指针（~几十字节/节点）
   
   单页（4KB）容纳：
   - B+Tree：100+ 个分支
   - 红黑树：几十个节点
   ```

3. **预读友好**
   ```
   B+Tree 叶子节点连续存储，可利用磁盘预读
   红黑树节点分散，随机访问多
   ```

### Q2: B+Tree 的范围查询为什么快？

**A**：链表结构是关键

```
普通 B-Tree：
        [50]
       /    \
    [25]    [75]
   /   \    /   \
  10   30  60   90
  
范围查询 [20, 60]：
1. 找到 25（中序遍历）
2. 回溯到根
3. 下降到 75
4. 找到 60
需要多次回溯！

B+Tree：
         [50]
        /    \
    [25]      [75]
   /   \     /   \
[10,25] [30,50] [60,75] [90]
  ↓       ↓       ↓      ↓
链表连接：10->25->30->50->60->75->90

范围查询 [20, 60]：
1. 定位到 25
2. 沿链表扫描：25->30->50->60
3. 遇到>60 停止
无需回溯！
```

### Q3: Hash 索引有什么优缺点？

**A**：

**优点**：
1. 等值查询 O(1)，最快
2. 实现简单
3. 适合 KV 存储

**缺点**：
1. ❌ 不支持范围查询
2. ❌ 不支持有序遍历
3. ❌ 存在哈希冲突
4. ❌ 扩容成本高（rehash）

**适用场景**：
- ✅ Redis、Memcached（内存 KV 存储）
- ✅ 精确匹配的场景
- ❌ 不适合数据库主索引

### Q4: InnoDB 的聚簇索引是什么？

**A**：数据与索引在一起

```
普通索引（二级索引）：
  索引结构 -> 指向数据行
  
聚簇索引（主键索引）：
  叶子节点 = 数据行本身
  
示例：
CREATE TABLE users (
  id INT PRIMARY KEY,      -- 聚簇索引
  name VARCHAR(50),
  age INT,
  INDEX idx_age (age)      -- 二级索引
);

聚簇索引 B+Tree：
         [id=50]
        /       \
    [id=25]   [id=75]
   /     \     /     \
[id=10, 数据] ... [id=90, 数据]
  ↑ 叶子节点直接存储整行数据
```

**优势**：
- 主键查询无需回表
- 数据物理聚集，I/O 少

**劣势**：
- 二级索引需要回表
- 插入依赖主键顺序

## 📝 核心要点总结

### 一句话答案

**InnoDB 选择 B+Tree 是因为它在磁盘 I/O、范围查询、排序优化三个方面都有最佳表现，特别适合 OLTP 场景。**

### 三个关键点

1. **磁盘友好** - 树高低，I/O 少
2. **范围查询** - 链表结构，扫描高效
3. **排序优化** - 天然有序，无需额外排序

### 对比记忆法

```
B+Tree vs 红黑树：
- 高度：3 层 vs 20 层（胜 6 倍）
- I/O：3 次 vs 20 次（胜 6 倍）
- 范围：链表扫描 vs 中序遍历（胜 10 倍）

B+Tree vs Hash：
- 等值：O(log n) vs O(1)（败）
- 范围：O(k) vs O(n)（胜 100 倍）
- 排序：天然 vs 需要（胜）
```
