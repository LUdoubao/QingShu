## 🎯 核心知识点

### 一、慢 SQL 定义

- 执行时间超过阈值的 SQL
- 通常指超过 1s 或 2s 的查询
- 影响系统性能的关键因素

### 四、步骤 2：分析

#### 使用 EXPLAIN 等工具分析

**示例分析**：
```sql
SELECT * FROM users WHERE name LIKE '%张%';
-- 执行时间：2500ms
```

**EXPLAIN 输出**：
```
┌─────────────┬──────────────────────────┐
│   字段      │          值              │
```

**性能分析**：
```
【执行时间】2500ms - ❌ 很慢
【扫描行数】100000 行 - ❌ 太多（扫描/返回=200.0）
【访问类型】ALL - ❌ 差
【Extra】Using where - ℹ️  普通
```

**优化建议**：
```
1️⃣  扫描行数过多，考虑添加索引
2️⃣  全表扫描，必须在 WHERE 列上加索引
```

### 五、步骤 3：改造

#### 针对性优化方案

##### 场景 1：前导 % 模糊查询

**原 SQL**：
```sql
SELECT * FROM users WHERE name LIKE '%张%';
问题：前导 % 导致全表扫描
```

**优化方案 1：使用全文索引**
```sql
ALTER TABLE users ADD FULLTEXT INDEX ft_name (name);
SELECT * FROM users WHERE MATCH(name) AGAINST('张');
效果：从 2500ms → 50ms
```

**优化方案 2：避免前导 %**
```sql
-- 如果业务允许，改为后缀匹配
SELECT * FROM users WHERE name LIKE '张%';
效果：从 2500ms → 10ms
```

**优化方案 3：搜索引擎**
```sql
-- 复杂场景使用 Elasticsearch
效果：从 2500ms → 20ms
```

---

##### 场景 2：深分页

**原 SQL**：
```sql
SELECT * FROM orders 
ORDER BY create_time DESC 
LIMIT 100000, 20;
-- 执行时间：1800ms
```

**问题分析**：
- 需要扫描前 100020 行
- 丢弃前 100000 行，只取 20 行
- 效率极低

**优化方案 1：延迟关联**
```sql
SELECT o.* 
FROM orders o
INNER JOIN (
    SELECT id 
    FROM orders 
    ORDER BY create_time DESC 
    LIMIT 100000, 20
) tmp ON o.id = tmp.id;
-- 效果：从 1800ms → 100ms
```

**优化方案 2：记录上次位置**
```sql
-- 第一次
SELECT * FROM orders 
ORDER BY create_time DESC 
LIMIT 20;
-- 记录最后一条的 create_time

-- 后续
SELECT * FROM orders 
WHERE create_time < '上次最后时间'
ORDER BY create_time DESC 
LIMIT 20;
-- 效果：从 1800ms → 50ms
```

---

##### 场景 3：大事务

**原 SQL**：
```sql
-- 一个事务处理 10000 条数据
START TRANSACTION;
  UPDATE ... WHERE batch_id = 1;
  UPDATE ... WHERE batch_id = 2;
  ...
COMMIT;
-- 执行时间：950ms
```

**优化方案：拆分事务**
```sql
-- 拆分为多个小事务
UPDATE ... WHERE batch_id = 1;
UPDATE ... WHERE batch_id = 2;
...
-- 效果：减少锁等待，降低死锁风险
```

### 六、步骤 4：验证

#### 压测看 p95/p99，不只看平均值

**压测指标对比**：

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| **avg (平均)** | 2500ms | 50ms | 50x |
| **p95** | 3200ms | 80ms | 40x |
| **p99** | 4500ms | 120ms | 37.5x |
| **QPS** | 100 | 5000 | 50x |

**关键点**：
- ✅ 不能只看平均值（avg）
- ✅ 要看 p95/p99（长尾延迟）
- ✅ QPS 提升 50 倍

**为什么看 p95/p99？**
```
【示例】100 次请求的延迟分布：
  95 次：10ms
  4 次：100ms
  1 次：10000ms

avg = (95*10 + 4*100 + 1*10000) / 100 = 113.5ms
p95 = 100ms（第 95 百分位）
p99 = 10000ms（第 99 百分位）

→ avg 看起来不错，但 p99 有 10s 延迟！
→ 用户体验很差
```

## 📊 常见优化手段总结

| 问题类型 | 优化方案 | 说明 |
|---------|---------|------|
| **全表扫描 ALL** | 加索引 | WHERE 列必须加索引 |
| **扫描行数多** | 联合索引 | 减少回表次数 |
| **Using filesort** | ORDER BY 索引 | 避免外部排序 |
| **Using temporary** | GROUP BY 索引 | 避免临时表 |
| **回表多** | 覆盖索引 | 查询列都在索引中 |
| **深分页** | 延迟关联 | 先 ID 后数据 |
| **大事务** | 拆分事务 | 减少锁等待 |
| **前导 %** | 全文索引 | 或改用搜索引擎 |

## 🔍 经典面试题

### Q1: 慢 SQL 如何定位？

**A**: 
- 开启慢查询日志
- 设置合适的阈值（如 1s）
- 定期分析慢查询日志
- 找出执行时间最长的 TopN SQL
- 优先优化最慢的

### Q2: 分析 SQL 性能用哪些工具？

**A**:
- **EXPLAIN**：查看执行计划（最重要）
- **SHOW PROFILE**：分析各阶段耗时
- **SHOW PROCESSLIST**：查看当前执行
- **performance_schema**：详细性能数据
- **pt-query-digest**：分析慢查询日志

### Q3: 为什么优化要看 p95/p99，不看平均值？

**A**:
- 平均值会被大部分快速请求拉低
- p95/p99 反映长尾延迟
- 用户体验取决于最慢的请求
- 例如：99 次 1ms + 1 次 10s，avg=101ms，但 p99=10s

### Q4: 常见的 SQL 优化手段有哪些？

**A**:
- 添加合适的索引
- 使用覆盖索引减少回表
- 避免 SELECT *
- 优化分页（延迟关联）
- 大事务拆小
- 避免文件排序和临时表
- 使用连接池
- 读写分离

### Q5: 如何验证优化效果？

**A**:
- 压测对比优化前后的指标
- 关注 p95/p99 延迟
- 关注 QPS 变化
- 上线后持续监控
- 确保没有引入新问题
